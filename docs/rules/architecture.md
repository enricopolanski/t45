# Architectural rules

- `model`s describe the entities involved in the application such as Users or Agents. They are closely related to what gets saved in Repositories.
- `model`s reflect data as it makes sense from a business-logic perspective, they don't bend to make storage or wire-transport easier
- `resource`s reflect how a data gets sent over the wire. Resources can be aggregates of different data. An `Automation` model may refer to the agent carrying it simply by id (e.g. `agentId: StringId`) but some `AutomationView` may carry details about the agent (name, tools, etc).
- `resource`s define the views and capabilities of an endpoint: what is the accepted payload, what is the response (generally a view or a model), what are the errors
- `core` holds pure application behavior shared by web and server, such as parsing and formatting message references. Model invariants stay in contracts. Core depends on contracts; contracts never depend on core. UI behavior stays in web, and provider-specific formatting stays in server.
- `model`s may implement business-logic rules through pure functions. E.g. If implementing operations to remove an admin from an organization or a workflow instance, models may implement helper functions or classes to model the impossibility to remove an admin if it would leave the entity without any admin. In fact, as much pure business-logic as possible should live in models and sometimes resources, so it can be reused by other consumers and stay consistent without the need to implement it multiple times. E.g. you don't want to define multiple times the admin removal rules, so it's better to do it in models and resources
- keeping business logic in contracts means that some logic that commonly goes on storage layer (e.g. a SQL database can enforce many business logic rules) is not placed there or its duplicated. This is a known and accepted cost. It's better to have testable logic that is independent from implementation details like storage or wire or UI than spread it in multiple places.
