## Why

amazon.de blocked the agent's own Chromium after a few searches with its 503 "Tut uns Leid!" page, and every agent on a runner browses from the runner's IP. Being blocked is not acceptable. "Web browser" is now a T45 capability. Whoever manages an agent turns it on in the editor, next to Network. Playwright CLI stays in the VM and keeps giving the agent the same commands and compact page reads. It now connects over CDP to a browser that runs elsewhere, so only the browser moves. The first provider is Bright Data's Browser API, with residential IPs, a German IP via `-country-de`, and CAPTCHA handling.

## How the credential stays out of the agent

1. The server holds `WEB_BROWSER_URL`: the browser's CDP WebSocket URL, with the credential as user and password. The name doesn't depend on the provider. When it is unset, no agent gets a browser.
2. For an agent with Web browser, the server sends the URL with each execution. Agents without it get nothing.
3. The runner splits the URL:
   - the VM may reach only that host and port;
   - TLS on that port is intercepted;
   - the credential becomes a microsandbox secret bound to that host, substituted only into the `Authorization` header.
4. Playwright CLI in the VM gets the endpoint without the credential, through `PLAYWRIGHT_MCP_CDP_ENDPOINT`. Its `Authorization` header, set through `PLAYWRIGHT_MCP_CDP_HEADERS`, holds only a placeholder. The VM, its saved disk and the agent never see the credential.

Web browser works with either Network setting, because the browser's host gets its own egress rule. The network note an agent reads covers four cases: no internet, a browser only, the internet with a browser, and the internet without one.

## Waiting for your decision: agent capabilities out of the server

Adding Web browser touched 14 files: the schema, the server's agent repository, its config and execution request, the web editor and the runner. The server ends up knowing how capabilities are realized, through MCP commands, VM paths, CDP settings and provider credentials.

The proposal is a package, `packages/agent-capabilities`, holding a static list of capabilities: internet, web browser, step tools, project operations and workflow drafting.

- **Each capability** has a description the editor shows, and a setup only the runner applies: MCP servers, files, environment, network rules, secrets, and the note the agent reads.
- **The server** keeps only which capabilities each agent has, as one list, and who may change them. At execution it sends the ids and a neutral context: server URL, tool token, step or project id.
- **The editor** draws its switches from the list.
- **The runner** applies the setups and reads provider keys from its own environment.

With this, Web browser would have been one entry in the package plus a runner variable.

1. **Where the Bright Data credential lives.** The request put it on the server. In this design it belongs in the runner's environment, like the OpenCode key, so the server knows nothing about the provider. Agree, or did you mean "server side, outside the VM"?
2. **PR #10.** It isn't merged, and it adds the leak. Should I rebuild it as the capabilities package, with Web browser as its first new entry, rather than merge it and undo it later?

Nothing is written yet, and a plan comes before any code. The code of T45's own tools (step, project, workflows) stays in the server, since it calls the server's RPCs. Only how they are wired into the VM would move.
