# Runner refactor review

Reviewed the current implementation against `b66758b`, including callers, persistence, the RPC transport, the pinned dependency sources and the replacement tests; the production TypeScript change is a real net reduction of 439 lines, excluding tests and test fixtures.

Point 1 remains for discussion; deferred RPC, buffering and tool-packaging work is tracked in `cleanup.md`.

1. **[P1 · reproduced; for discussion] `ChatExecutions.stop` can change the state of a new run started while the previous run is stopping.** Here a replacement execution means a new run for the same chat, triggered by a new input while the previous run is still stopping. `stop` removes the chat from `runs` before waiting for the old fiber to stop, then discards uncommitted output and changes any `running` status to `interrupted` without checking which execution now owns it. I paused the old stream's cleanup, sent a new input, observed a second run take that input, and then resumed cleanup: the old stop marked the replacement chat interrupted. Its output can also be discarded by that old stop, and its eventual `finished` is ignored because `end` requires `running`. Keep one per-chat owner through stopping and process inputs committed during that stop afterward, rather than freeing the reservation early and letting cleanup operate on whichever run happens to exist later.

2. **[P2 · source verified; simplification] Send the newly posted input instead of reconstructing every pending input on every post.** The running branch of `ChatExecutions.processInputs` rereads the full pending list, formats every prompt, rereads its attachments, and sends all of them over RPC. The runner then ignores ids it already knows, after those bytes have crossed the network. With N inputs queued behind a long turn, this produces roughly N-squared input submissions and can repeatedly upload the same large attachments. `ChatService.post` already has the exact new input: pass it to delivery once, leaving the full pending scan for starting or recovering an execution and checking completion.

3. **[Simplification · substantial] Return a scoped VM handle from `Sandbox.start` and remove the second VM registry.** `Executions` already owns each attempt and its lifetime, but `Microsandbox` keeps another `started` map and implements `held`, `write(id, ...)`, `pack(id)`, `unpack(id, ...)` and `remove(id)` by repeatedly looking up that mutable map. Have acquisition return the server and operations bound to the actual VM, with destruction registered on its scope immediately after creation. That removes the map, missing-handle branches, repeated lookups and the execution's manual remove finalizer, while making cleanup target the acquired VM rather than the latest VM under the same id. A failed or interrupted setup still needs cleanup; scope acquisition handles that without a separate lifecycle table.

4. **[Simplification · explicit performance tradeoff] Full reads of marked sessions could remove much of `Capture`'s bookkeeping.** The combination of `cursors`, `seen`, per-message settled flags and touched-message sets exists to incrementally read growing sessions while rereading earlier mutable messages. If the product accepts rereading a marked session's complete message list per batch, `marks.sessions` can become a set of session ids and the cursor/settled/touched machinery can go. Keep live messages and the final read-and-check; `session.export` is not a drop-in replacement because the pinned implementation omits unsettled messages. This would substantially cut state, but increases read/transfer cost with conversation length and applies the 64 MiB response cap to a whole session, so it is a product/performance choice, not an unconditional deletion.

5. **[Simplification · dependency source verified] Session-tree pagination can be removed independently of message pagination.** `OpenCode.listSessions` has a comment saying OpenCode rejects `cursor` with `order`, but the pinned `Session.list` instead ignores supplied filters when a cursor exists; the rejection belongs to message listing. Session-list `limit` has no schema maximum, so `Capture.readTree` can fetch the VM's session infos in one call with a sufficiently large limit and delete the pagination helper and its `Option` dependency. The tradeoff is that the 64 MiB response cap then covers all session infos together; retain message pagination unless separately accepting point 4. This candidate is already in `simplification-review.md` and remains valid.

6. **[Simplification · source verified] `ExecutionFailed.reason` is transported but never consumed.** T45 only distinguishes retryable `RpcClientError` from everything else and never reads this error's tag or reason; the runner already logs the original error. With `disableFatalDefects: true`, an unexpected execution defect is confined to that RPC call and can carry its diagnostic message through Effect's defect encoding. If the contract does not need a future typed failure API, remove `ExecutionFailed`, its schema entry and the mapping/fake branches, using the RPC failure channel instead. The tradeoff is losing the explicit typed declaration, not changing current chat behavior; this is also already identified in `simplification-review.md`.

7. **[Simplification · source verified, behavior choice] The workflow attach-path regex duplicates the generated-file lookup.** `WorkflowService.taskHooks.prepare` accepts bytes only from the current execution's `generated` map, and that map only receives file events for paths the runner listed in `.t45/attached`. The UUID regex therefore adds a filename convention rather than another host-filesystem boundary. If arbitrary names within the emitted snapshot set are acceptable, delete the regex and keep the exact map lookup; update the security explanation accordingly. A forged receipt naming a non-UUID file in that directory would then work, so describe this as relaxing a convention, not as a behavior-preserving deletion; this candidate is also already in `simplification-review.md`.

Validation: `vpr pre-commit` passed with all tasks served from cache, a fresh focused run passed all 27 tests in `Executions.test.ts`, `OpenCode.test.ts` and `ChatExecutions.test.ts`, and temporary diagnostics outside the repository reproduced lifecycle races and smoke-checked a real HTTP `run` carrying binary request values; no implementation files were changed for this review.
